VPI / direct model / compiler target

VPI is an IEEE-defined programming interface into an HDL simulator. It is not cocotb. The existing SharpTestBench bridge has owned C++20 ABI functions and direct-packed optimizations, but its full production startup/callback/object layer still loads a cocotb-derived GPI library. The isolated VPI probe and the direct-Verilator example do not, by themselves, prove a complete independent C# runtime.

Do not claim “cocotb-free full framework” until the complete managed test assembly launches and finishes without libgpi, upstream bootstrap, or cocotb tooling.
02 / Standard interface

What VPI actually does

Discover objects

vpi_handle_by_name, vpi_handle, vpi_iterate and vpi_scan locate modules, ports, variables and hierarchy.

Inspect or change values

vpi_get_value/vpi_put_value handle scalar, integer, string, real and packed vector formats. Four-state values use aval/bval encoding.

Register simulation events

vpi_register_cb subscribes to edges, time delays, read/write synchronization and end-of-simulation events. Handle removal/lifetime matters.

// Typical VPI shape, error checks omitted for illustration
vpiHandle signal = vpi_handle_by_name(
    const_cast<PLI_BYTE8*>("top.data"), nullptr);
s_vpi_value value{};
value.format = vpiVectorVal;
vpi_get_value(signal, &value);
// Bits are represented in value.value.vector[] (aval/bval).

Why use VPI? It provides a stable conceptual interface across multiple simulators. Why bypass it? Runtime lookups, handle indirection, callback registration, conversions and generic compatibility semantics may cost more than directly reading a generated C++ member. The size of that cost must be measured for the actual test workload.

03 / Timing contract

No lost clocks, no collapsed delta cycles

Drive

Write test inputs at a defined phase. Deposits scheduled for ReadWrite should become visible according to each simulator’s scheduler contract.

Evaluate

A simulator processes combinational propagation and clocked updates; a Verilated C++ model requires calls to eval() or eval_step().

Sample

Read the settled outputs in the appropriate observation phase. A write does not automatically mean all dependent logic has propagated.

Verilator is compiled rather than a traditional event-interpreted engine. Its documentation explicitly notes that a VPI write does not necessarily propagate until model evaluation. Direct C++ port writes share that requirement. A replacement driver must preserve each rising edge and all relevant combinational stabilization semantics. Read/write batching is safe only within a compatible simulation phase, not across distinct cycles.

A fast access path is not semantically interchangeable with another unless edge-capture tests, reset cuts, callback ordering and full cycle traces agree.
04 / Non-VPI execution

Direct access to Verilator's generated model

Verilator generates a native class such as Vcounter. Top-level ports are accessible as C++ members. Internal signals may be exposed using explicit public pragmas or via rootp and the generated root header. The generated layout is a build artifact, not a stable cross-version ABI.

#include "Vcounter.h"
#include "verilated.h"
Vcounter dut;
dut.reset = 1;
dut.clk = 0; dut.eval();
dut.clk = 1; dut.eval();  // reset edge
dut.clk = 0; dut.eval();
dut.reset = 0;
dut.clk = 1; dut.eval();  // next active edge
auto observed = dut.count;
dut.final();

The C++20 direct-model example runs 100,000 counter edges and checks the expected state after every rising edge, without VPI or cocotb. It is intentionally a proof of model-port access—not yet a replacement for all SharpTestBench scheduler callbacks.

Do not blanket-enable --public or --public-flat-rw just to make discovery convenient. Prefer explicit public signals required by the verification contract. For generated designs, SharpTestBench could eventually generate a typed C++20 access shim and a compact metadata manifest mapping stable logical signal IDs to native member accessors.

05 / Icarus-specific tools

Not everything is VPI on Icarus either

Icarus offers the standard runtime VPI module mechanism (iverilog-vpi and vvp -m) and a separate nonstandard loadable elaboration-target API in ivl_target.h. The latter runs during compilation, not simulation, and can inspect the elaborated design.

Runtime VPI

Read/write live signals, attach callbacks, manage simulator time. This is the natural standalone runtime extension for Icarus.

Loadable target

Extract dimensions, structural metadata and connectivity at elaboration time. SharpTestBench already includes native/icarus_layouts.cpp for related metadata.

Potential improvement: generate typed bindings and packed layout metadata once at elaboration, then avoid repeated reflection/hierarchy traversal at runtime. The Icarus target API is not a substitute for runtime VPI callbacks, and its data should not be treated as portable across simulator versions without explicit schema/version checks.

07 / Decision experiment

Profile a real RISCue program before further optimization

RISCue is a five-stage RV32 processor with ECC/TMR, UART, AXI and compiled C programs. A useful comparison should hold the program, RTL, cycle count, observable ports, correctness oracle and trace settings fixed.

A

HDL-only

Compiled Verilator model with minimal C++ host, same CPU program and correctness digest.

B

VPI managed

Full SharpTestBench C# driver and scoreboard, with counters for native transfers and managed work.

C

Direct model

Equivalent port-only C++20 host, preserving clock/evaluation contract and comparing architectural trace.

Report separate HDL evaluation time, model-build time, test-body time, process wall time, CLR allocations and collections, native calls by type and width, logical versus physical bytes transferred, number of callbacks and retired instructions. Use at least seven alternating timed runs on the same host. A sampling profiler and existing Verilator execution profiling should precede any Verilator fork.

At present, SharpTestBench’s production managed bridge is hybrid and still requires cocotb GPI. The C++ direct-model sample is independent, but only tests generated ports. Benchmark the full independent backend only after it can run the same C# test assembly.
